# Design

## Context

- Next.js 16 App Router с `cacheComponents`, React 19, Drizzle + postgres.js, PostgreSQL 18. Сейчас входа нет: все запросы в `src/lib/contacts.ts` и `src/lib/groups.ts` работают со всей базой, а серверные действия в `src/app/actions.ts` принимают номера записей от браузера. Номера, привязанные через `.bind`, браузер может подменить, поэтому проверять владельца должен только сервер
- Названия групп уникальны по всей базе: индекс `groups_lower_name_idx` на `lower(name)`
- Выкатка: бэкап → разовый контейнер `migrate` (сейчас `drizzle-kit migrate`) → новый образ → `/health`. nginx передаёт приложению `X-Forwarded-For`
- e2e: Playwright, своя база `personal_crm_e2e`, пересоздаётся при каждом запуске и заполняется 1000 контактами; в CI тесты идут на собранном приложении (`next start`)
- Репозиторий открытый: личные данные и секреты в git не попадают
- Требования: `specs/user-auth`, `specs/data-ownership`, `specs/contact-groups` этого изменения

## Goals / Non-Goals

**Goals:**

- Один способ входа по ссылке из письма, сделанный готовой библиотекой, а не своим кодом токенов и сессий
- Владелец проверяется в каждом запросе к базе, а не только в интерфейсе
- Одна сборка приложения работает и локально, и на сервере: куда слать письма, решают переменные окружения
- Миграция данных проходит за одну выкатку и откатывается вместе с базой из бэкапа

**Non-Goals:**

- Правила доступа в самой базе (RLS), роли, общий доступ
- Почта на сервере по API почтового сервиса: только SMTP, как и локально
- Хранение ограничений по IP в базе: встроенный ограничитель библиотеки держит их в памяти процесса, у нас один процесс

## Decisions

### 1. Better Auth с плагином magic link и адаптером Drizzle

Задано в `specs/02`. Версии — последние стабильные на момент установки, которые пропускает защита pnpm от слишком свежих версий (не моложе суток). На 2026-11-08 это `better-auth` и `@better-auth/drizzle-adapter` 1.7.18 (в 1.7.16+ закрыты уязвимости, найденные 2026-11-03) и `nodemailer` 10.3.1. Схема таблиц генерируется CLI `auth generate --adapter drizzle` (пакет `auth`, а не устаревший `@better-auth/cli`) в `src/db/auth-schema.ts`, миграция — обычным `drizzle-kit generate`.

- Таблицы во множественном числе (`usePlural`): `users`, `sessions`, `accounts`, `verifications`. Так не нужно экранировать зарезервированное слово `user` в SQL и psql
- Экземпляр `auth` создаётся лениво (`getAuth()`), как `getDb()`: без этого `next build` требовал бы секрет входа
- Обработчик `src/app/api/auth/[...all]/route.ts` через `toNextJsHandler`. Плагин `nextCookies()` последним: он ставит cookie из серверных действий

Альтернатива — свой код ссылок и сессий. Отклонена: больше кода безопасности, а требования прямо называют библиотеку.

### 2. Запрос ссылки — серверное действие, правила почты — в хуке библиотеки

Форма входа — клиентский компонент с `useActionState`. Действие `requestSignInLinkAction` проверяет почту (zod: обрезка, нижний регистр, формат) и вызывает `auth.api.signInMagicLink`. Ответ «Ссылка для входа отправлена на <почта>» одинаковый для новой и известной почты: библиотека в обоих случаях отправляет письмо.

Те же правила должны работать и при запросе в обход формы на `/api/auth/sign-in/magic-link`. Поэтому они живут в `hooks.before` для пути `/sign-in/magic-link`, который срабатывает и для HTTP, и для `auth.api`:

1. Почта приводится к виду без пробелов и в нижнем регистре, неверный адрес — ошибка 400. Плагин сам почту не нормализует
2. Лимит: если на эту почту за 10 минут ушло 3 письма, ошибка `TOO_MANY_REQUESTS`. Отправки учитываются в своей таблице `magic_link_sends (id, email, sent_at)`, запись появляется после успешной отправки. Встроенный ограничитель считает только по IP, а серверные вызовы `auth.api` не ограничивает вовсе
3. Новая ссылка гасит старые: хук удаляет из `verifications` прежние ссылки этой почты, плагин потом записывает новую. Сам плагин старые ссылки не гасит

Ссылки хранятся хешем (`storeToken: "hashed"`): утечка базы не даёт рабочих ссылок. Срок `expiresIn` — 900 секунд. Одноразовость обеспечивает плагин.

### 3. Куда ведёт ссылка

`callbackURL` и `newUserCallbackURL` — `/`, `errorCallbackURL` — `/login`, библиотека сама добавляет `?error=<код>`. Плагин отдаёт одну ошибку `INVALID_TOKEN` и для истёкшей, и для использованной, и для неизвестной ссылки. Страница входа с любым `error` показывает «Ссылка устарела, запроси новую» и кнопку на чистую страницу входа. Вошедшего пользователя страница входа переводит на главную.

### 4. Сессия 30 дней с продлением, проверка в `proxy.ts` и в каждом запросе к данным

`session.expiresIn` 30 дней, `updateAge` 1 день: при заходе, если с прошлого продления прошли сутки, срок снова 30 дней. Cookie `httpOnly`, `SameSite=Lax`; `Secure` и префикс `__Secure-` — когда адрес сайта `https` (на сервере). Выход — `auth.api.signOut`, удаляет только сессию этого устройства.

Защита в два слоя:

- `src/proxy.ts` для всех путей, кроме `/login`, `/api/auth`, `/health` и статики, вызывает `auth.api.getSession` и пересылает в ответ продлённую cookie. Без сессии — переход на `/login`. Здесь же происходит продление: из серверного компонента cookie поставить нельзя, а библиотека в запросах с заголовком `RSC` продление пропускает. Поэтому proxy передаёт заголовки без `RSC`
- `requireUserId()` в `src/lib/session.ts`: каждое серверное действие и каждая страница с данными берут пользователя только отсюда. Нет сессии — у страниц переход на `/login`, у действий отказ без изменений. proxy — не защита: matcher может что-то пропустить

Альтернатива — только оптимистичная проверка cookie в proxy (`getSessionCookie`). Отклонена: тогда продление пришлось бы делать отдельным запросом из браузера на каждой странице.

Шапка с почтой и «Выйти» читает сессию, то есть это динамические данные. С `cacheComponents` она стоит внутри `Suspense`, как и остальные динамические части.

### 5. Владелец в каждом запросе

- `contacts.owner_id` и `groups.owner_id`: `text not null`, ссылка на `users.id` с `on delete cascade`. Заметки и `contact_groups` своего поля не получают, владелец берётся через контакт и группу
- Все функции в `src/lib/contacts.ts` и `src/lib/groups.ts` первым параметром принимают `ownerId` и добавляют его в `where` каждого запроса, в том числе в изменения и удаления. Заметки проверяются через контакт, связи с группами — через контакт и через группу. Чужая запись выглядит как несуществующая: те же `not-found` и «Контакт не найден», что и для удалённой
- Уникальный индекс группы — `(owner_id, lower(name))` вместо `lower(name)`
- Индексы под новые запросы: `contacts (owner_id, name)`, `groups (owner_id)`
- Правило из CLAUDE.md («каждый запрос отдаёт только данные текущего пользователя»): новые функции пишутся так же

### 6. Миграция данных: почта владельца из настроек, одна транзакция

Вместо `drizzle-kit migrate` миграции применяет `scripts/migrate.ts`: `migrate()` из drizzle-orm, как уже делает `e2e/global-setup.ts`. Перед этим скрипт кладёт `OWNER_EMAIL` в настройку сессии Postgres `app.owner_email`. Скрипт работает и в `pnpm db:migrate`, и в контейнере `migrate` на сервере.

Миграция `0003` генерируется `drizzle-kit generate` и правится руками:

1. Новые таблицы входа и `magic_link_sends`; `owner_id` добавляется пока без `not null`
2. Блок `DO`: если в базе есть контакты или группы, берёт почту из `app.owner_email` (обрезка, нижний регистр). Если почты нет — `RAISE EXCEPTION`: миграция откатывается целиком, выкатка останавливается, работает прежняя версия. Иначе создаёт пользователя с этой почтой, если его ещё нет, и записывает его в `owner_id` всех контактов и групп
3. `owner_id set not null`, замена индексов

drizzle-orm применяет все новые миграции одной транзакцией, поэтому половинчатого состояния нет. В пустой базе (e2e, CI, новый компьютер) блок ничего не делает, и почта не нужна.

Альтернатива — почта в SQL-файле. Отклонена: она попала бы в открытый репозиторий. Ещё альтернатива — отдельная команда после миграции. Отклонена: тогда `not null` пришлось бы ставить следующей выкаткой, это лишний ручной шаг.

### 7. Письма: Nodemailer по SMTP, адрес сервера в одной переменной

`src/lib/mailer.ts`: `createTransport(process.env.SMTP_URL)`, отправитель из `MAIL_FROM`. Транспорт создаётся при первой отправке.

- Локально и в CI: `SMTP_URL=smtp://127.0.0.1:1025`, это Mailpit
- На сервере: `smtps://resend:<ключ>@smtp.resend.com:465`, ключ только в `.env` сервера

Письмо — HTML и текстовая версия: кнопка «Войти», срок «15 минут», фраза про то, что вход не запрашивали. `MAIL_FROM` — `Personal CRM <noreply@mail.app.vladmath.com>`.

Mailpit: образ `axllent/mailpit`, последний стабильный тег на момент установки. Порты 1025 и 8025 только на `127.0.0.1` в `docker-compose.yml`, сервис в e2e-задаче CI.

Nodemailer 10 поставляет свои типы, `@types/nodemailer` не ставим.

### 8. Встроенный ограничитель по IP

Включён в production, хранит счётчики в памяти. Для `/magic-link/verify` ослабляем до 30 открытий в минуту: e2e в CI открывают много ссылок с одного адреса, а подбор 32-символьной ссылки и так невозможен. IP берётся из `X-Forwarded-For`, nginx его уже передаёт.

### 9. Настройки

| Переменная | Локально | CI | Сервер |
|---|---|---|---|
| `BETTER_AUTH_SECRET` | своя, 32+ символа | разовое значение в workflow | своя, в `.env` |
| `BETTER_AUTH_URL` | `http://localhost:3000` | `http://localhost:3100` | `https://app.vladmath.com` |
| `SMTP_URL` | Mailpit | Mailpit | Resend |
| `MAIL_FROM` | общий | общий | общий |
| `OWNER_EMAIL` | почта владельца | не нужна: база пустая | почта владельца |

`.env.example` получает имена без значений. Строки в `.env` вписывает владелец.

### 10. Тесты

- Все существующие e2e идут под пользователем-владельцем тестовой базы. `global-setup` создаёт его, заполняет 1000 контактами и входит через Mailpit, сохраняя состояние браузера (`storageState`, файл в `.gitignore`). Тест «другой браузер» в главном сценарии получает то же состояние
- Помощник `e2e/mailpit.ts`: найти последнее письмо на адрес (`/api/v1/search?query=to:...`) и вытащить из него ссылку. У каждого теста свои адреса: поиск `to:` ищет подстроку
- Новые e2e: `login.spec.ts` — сценарии `user-auth`; `data-ownership.spec.ts` — два пользователя, группы, «Пора связаться», прямые запросы. Прямой запрос: тест перехватывает настоящий запрос серверного действия от B к его записи и повторяет его с номером записи A, потом проверяет, что у A ничего не изменилось
- Сроки ссылок, писем и сессий тесты сдвигают прямо в тестовой базе, как уже делают тесты «Пора связаться»
- `owner-migration.spec.ts`: временная база, миграции до `0002`, данные, затем остальные миграции с почтой и без неё
- Unit: проверка и приведение почты, текст письма

## Risks / Trade-offs

- [Миграция меняет все строки и индекс групп] → Бэкап перед миграциями уже в выкатке. До merge показываем SQL владельцу. Откат по README: прошлая версия приложения, затем база из бэкапа
- [Владелец забыл `OWNER_EMAIL` на сервере] → Миграция падает до изменений, прежняя версия работает. Строку проверяем вместе с владельцем до выкатки
- [Письма не доходят: домен не подтверждён в Resend или письмо в спаме] → Домен подтверждаем до выкатки. Если письмо не пришло, видно в журнале приложения и в панели Resend
- [Одна сессия на устройство живёт 30 дней] → Выход удаляет сессию сразу. Удаление пользователя не входит в изменение
- [Ограничитель по IP в памяти сбрасывается при перезапуске] → Приемлемо: главный лимит по почте хранится в базе
- [Хеш ссылки: при сбое отправки письма старые ссылки уже погашены] → Пользователь просто запрашивает снова
- [Продление сессии зависит от поведения библиотеки в proxy] → Сценарий продления покрыт e2e на собранном приложении

## Migration Plan

1. До выкатки владелец: подтверждает домен `mail.app.vladmath.com` в Resend, вписывает в `.env` сервера `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL`, `MAIL_FROM`, `OWNER_EMAIL`
2. Выкатка как обычно: бэкап → `scripts/migrate.ts` (схема и владелец) → новая версия → `/health`
3. Проверка: владелец входит своей почтой и видит прежние контакты; другая почта — пустой список
4. Откат — только вместе, по README: `deploy.sh` с прошлой версией, затем `restore.sh` с бэкапом, снятым перед этой выкаткой
