Вход по ссылке из письма

Каждый входит под своей почтой, без пароля: вводит адрес и открывает ссылку из письма. Внутри человек видит и меняет только свои контакты. Всё, что уже лежит в базе, при выкатке достанется вам как владельцу приложения.

1Коротко

  • Без входа открывается только страница входа: поле «Почта» и кнопка «Получить ссылку».
  • Вход — по ссылке из письма (magic link, «волшебная ссылка»: сама ссылка служит пропуском, пароль не нужен). Ссылка работает один раз и 15 минут.
  • Первый вход и есть регистрация (создание учётной записи). Имя не спрашиваем.
  • Вход держится 30 дней с последнего захода на этом устройстве. В шапке — почта и кнопка «Выйти».
  • У каждого контакта и каждой группы появляется владелец. Чужие данные для человека как будто не существуют.
  • Все контакты, заметки и группы, которые уже есть в базе, при выкатке получат владельца — пользователя с почтой из настроек сервера. Ни одна запись не теряется.
  • Статус: спроектирована, кода фичи ещё нет. Отмечено задач: 0 из 23. Автотестов (программ, которые сами проходят сценарий и сверяют результат) пока нет: они в плане и пишутся раньше кода — проверки входа, двух пользователей и переноса данных.

3Как это работает

Без входа — только страница входа

Все страницы приложения требуют входа. Открыты без входа только страница входа и служебная проверка /health (адрес, по которому выкатка проверяет, что приложение живо). Серверные действия (то, что сервер делает по кнопке: сохранить, удалить, добавить заметку) без входа ничего не меняют и данных не отдают.

Гость открыл адрес карточки app.vladmath.com/contacts/15 → видит страницу входа, имени и заметок контакта на ней нет.
Вход по ссылке из письма, первый вход — регистрация

Человек вводит почту, получает письмо, открывает ссылку — и он внутри, на главной. Если почта новая, пользователь создаётся сам, без формы и без вопроса об имени.

Гость открыл ссылку на карточку, вошёл по письму → попадает на главную, а не в ту карточку.
Почта приводится к одному виду

Пробелы по краям убираются, большие буквы становятся маленькими. Поэтому одна и та же почта, набранная по-разному, — один и тот же пользователь.

« Anna@Example.COM » → письмо уходит на anna@example.com, после входа Анна видит свои прежние данные.
Ответ не выдаёт, есть ли такой пользователь

После отправки всегда одно и то же «Ссылка для входа отправлена на <почта>» — и для новой почты, и для той, что уже входила. По ответу нельзя узнать, пользуется ли человек приложением.

Неверный адрес почты

Под полем — «Проверь адрес почты», письмо не уходит. Сервер проверяет адрес так же, даже если запрос пришёл в обход формы.

«anna@example» → «Проверь адрес почты», письма нет.
Не больше 3 писем за 10 минут на одну почту

Сверх этого — «Слишком часто, попробуй через несколько минут», письмо не уходит. Считается по почте, а не по устройству.

Анна запросила ссылку в 10:00, 10:02 и 10:05. В 10:07 → «Слишком часто…», письма нет. В 10:16 → письмо уходит: все три ушли больше 10 минут назад.
Ссылка: один раз, 15 минут, новая гасит прежние

Открыли ссылку — она больше не работает. Прошло 15 минут — тоже. Запросили новую — все прежние ссылки этой почты перестают работать. Во всех этих случаях видно «Ссылка устарела, запроси новую».

Анна запросила ссылку в 12:00, потом ещё одну в 12:03 → первая уже не работает, вторая работает до 12:18 и только один раз.
Вход держится 30 дней с последнего захода

Закрыли браузер — вход остаётся. Каждый заход продлевает вход: снова 30 дней с этого захода. Не заходили больше 30 дней — снова страница входа.

Вошли 1 ноября, заходили 20 ноября → вход действует до 20 декабря. Не заходили до 25 декабря → страница входа.
Несколько устройств сразу, выход — только на одном

Можно быть внутри с телефона и с ноутбука одновременно. «Выйти» завершает вход только на том устройстве, где нажали.

Анна нажала «Выйти» на телефоне → телефон показывает страницу входа, на ноутбуке она по-прежнему внутри.
У данных есть владелец

Контакт и группа принадлежат тому, кто их создал. Заметки принадлежат владельцу контакта. Кто владелец, сервер решает только по входу — не по данным из формы и не по адресу страницы.

Каждый видит только своё

Список, поиск, карточка, заметки, группы, фильтр по группе и блок «Пора связаться» показывают только данные того, кто вошёл. Чужой контакт по прямой ссылке — «Контакт не найден», как будто его нет.

Анна добавила Марию Кузнецову. Степан не найдёт Марию ни в списке, ни в поиске, а по ссылке на её карточку увидит «Контакт не найден».
Чужое не меняется даже прямым запросом

Сервер проверяет владельца при каждом изменении. Запрос с номером чужого контакта, заметки или группы ничего не меняет — как будто такой записи нет.

Степан отправил на сервер «удалить заметку №42», а это заметка к контакту Анны → ничего не удалено.
У каждого свои группы

Название группы не повторяется у одного пользователя, регистр не важен: «Теннис» и «теннис» — одно название. У разных людей названия друг другу не мешают. Остальные правила названия прежние: от 1 до 50 символов.

У Анны есть «Теннис». Степан вводит в карточке своего контакта «теннис» → у Степана создаётся своя группа, группа Анны не меняется.
Новый пользователь — пустой список

Кто вошёл впервые, видит пустой список и подсказку «Добавь первый контакт».

Всё, что уже есть, достаётся владельцу

При выкатке все контакты, заметки и группы из базы получают владельца — пользователя с почтой из настроек сервера (OWNER_EMAIL в .env, файле с настройками и секретами на сервере). Записей после выкатки ровно столько же, сколько до.

Вы входите своей почтой → видите все прежние контакты, заметки и группы. Другая почта → пустой список.
Тестовые данные — у владельца

Тестовые контакты, заметки, частоты и группы создаются у пользователя с почтой из OWNER_EMAIL. Тестовые группы — Семья, Друзья, Знакомые, Теннис, Аналитики, примерно треть контактов в одной или двух из них. Разовая команда тестовых групп ничего не меняет, если хотя бы одна группа уже есть.

4Модель данных до и после

Модель данных — какие таблицы лежат в базе и какие в них поля (колонки). Фича добавляет пять новых таблиц и поле владельца у контактов и групп. Заметки и «кто в какой группе» не меняются.

Сейчас

Четыре таблицы. У данных нет владельца: все контакты и группы общие. Название группы может быть только одно во всей базе.

Схему можно листать вбок.

После

Появляются пользователи и их входы. У контактов и групп — поле owner_id: номер пользователя-владельца. Названия групп уникальны у одного владельца.

новоекак было

Схему можно листать вбок.

  • users — пользователи. Строка появляется сама при первом входе по ссылке: это и есть регистрация.
  • sessions — входы. Один вход — одно устройство: телефон и ноутбук — две строки. «Выйти» удаляет строку только этого устройства. Браузер узнаёт свою строку по cookie (маленькой записи, которую сайт хранит в браузере).
  • verifications — ссылки из писем, пока ими не воспользовались. Хранятся хешем (необратимым отпечатком): даже из украденной базы по ним не войти.
  • accounts — служебная таблица библиотеки входа Better Auth.
  • magic_link_sends — учёт писем: на какую почту и когда ушло. По нему считается лимит «3 письма за 10 минут». Запись появляется после успешной отправки.
  • owner_id у контактов и групп — номер владельца, обязателен. Если пользователя удалить, удалятся и его контакты и группы. Удаления пользователя в этом изменении нет.
  • Заметки и «кто в какой группе» своего владельца не хранят: он берётся через контакт и группу.

Как запрос находит своё и не находит чужое

К каждому запросу в базу добавляется условие «и владелец — тот, кто вошёл». Кто вошёл, сервер знает только по входу. Пример: Мария Кузнецова — контакт №15 у Анны. Разные люди открывают один и тот же адрес /contacts/15.

Миграция

Миграция — скрипт, который меняет устройство базы. При выкатке она применяется сама, отдельным шагом до старта новой версии. Перед ней выкатка уже снимает копию базы (бэкап).

Миграция 0003: вход и владельцы меняет данные

Применяется одной транзакцией (пачкой изменений, которая проходит целиком или не проходит совсем). Если любой шаг падает, база остаётся ровно такой, как была.

  1. Новые таблицы данные не меняет

    users, sessions, accounts, verifications, magic_link_sends.

  2. Поле owner_id у контактов и групп данные не меняет

    Пока может быть пустым: иначе база не приняла бы старые строки без владельца.

  3. Всё, что есть, — владельцу меняет данные

    Если в базе есть контакты или группы, берёт почту из OWNER_EMAIL (убирает пробелы, делает буквы маленькими). Создаёт пользователя с этой почтой, если его ещё нет, и записывает его владельцем всех контактов и групп. Заметки и «кто в какой группе» переходят вместе с ними.

  4. Владелец обязателен, новое правило групп меняет правила

    Контакт или группу без владельца база больше не сохранит. Было: «название группы одно на всю базу», стало: «одно у владельца».

Шаг 3 спрашивает

В базе есть контакты или группы?

Нет, база пустая

Ничего не делает, почта не нужна. Так будет в автотестах и на новом компьютере.

Есть, а почта не задана

Ошибка. Миграция отменяется целиком, база не меняется, выкатка останавливается, работает прежняя версия.

Есть, почта задана

Всё получает владельца с этой почтой.

До выкатки — делаете вы

  • Подтверждаете домен mail.app.vladmath.com в Resend и создаёте ключ только на отправку с этого домена.
  • Вписываете в .env сервера новые строки, среди них OWNER_EMAIL — ваша почта. Строку проверяем вместе до выкатки.
  • Смотрите SQL миграции 0003 до merge: агент покажет его, как требует CLAUDE.md.

Как откатиться

Только вместе, по README (раздел «Бэкапы и восстановление»), запускаете вы:

  1. Сначала прошлая версия приложения: deploy.sh с прошлой версией.
  2. Потом база из копии, снятой перед этой выкаткой: restore.sh с этим файлом.

База вернётся к состоянию на момент копии. Сам откат не запускается никогда.

5Как проверить руками

Когда фича будет сделана. Сейчас проверять нечего: кода ещё нет. Шаги ниже — по каждому сценарию из трёх файлов требований.

Подготовка. Запустить приложение локально по README: база и почтовый ящик-заглушка Mailpit (docker compose up -d), новые строки в .env (список даст агент), pnpm db:migrate, pnpm dev. Письма приходят не в настоящую почту, а на страницу Mailpit — её адрес агент впишет в README.

Два пользователя. A — вы: почта из OWNER_EMAIL, у вас тестовые данные. B — новая почта, например stepan@example.com, в другом браузере или в окне инкогнито (частном окне, которое не видит входа основного).

Сроки в 10 минут, 15 минут и 30 дней руками можно только переждать; автотесты сдвигают время прямо в тестовой базе. Галочки на этой странице не сохраняются.

Технические — на экраны не влияют

  • Вход делает готовая библиотека Better Auth (задана в требованиях), а не свой код ссылок и входов: меньше своего кода безопасности.
  • Таблицы входа названы во множественном числе (users, а не user): слово user в базе занято.
  • Ссылки хранятся хешем: утечка базы не даёт рабочих ссылок.
  • Правила почты — приведение адреса, лимит, гашение старых ссылок — встроены в саму библиотеку через «хук» (место, куда библиотека даёт вставить свою проверку). Поэтому они работают и для запросов в обход формы.
  • Письма учитываются в своей таблице: встроенный ограничитель библиотеки считает только по IP-адресу (адресу устройства в сети) и не ограничивает вызовы с самого сервера.
  • Ограничитель по IP-адресу тоже включён на сервере, счётчики в памяти приложения. Для открытия ссылок ослаблен до 30 в минуту, чтобы автотесты не упирались в него. Сброс при перезапуске не страшен: главный лимит по почте хранится в базе.
  • Вход проверяется дважды: «привратник» перед каждой страницей (proxy) и ещё раз в каждом запросе к данным. Привратник может что-то пропустить, поэтому главная проверка — в запросе.
  • Продление входа делает привратник: если с прошлого продления прошли сутки, срок снова 30 дней.
  • Cookie входа недоступна скриптам страницы, а на сервере передаётся только по защищённому соединению (https).
  • Владелец проверяется в каждом запросе к базе: каждая функция работы с контактами и группами получает владельца и добавляет его в каждое условие поиска, изменения и удаления. Правил доступа внутри самой базы (RLS) нет.
  • Новые индексы (оглавления, по которым база быстро ищет): контакты по владельцу и имени, группы по владельцу.
  • Миграции применяет свой скрипт scripts/migrate.ts: он передаёт базе OWNER_EMAIL. Работает и локально, и при выкатке.
  • Почта владельца не записана в файле миграции — иначе попала бы в открытый репозиторий. Владелец ставится в ту же выкатку, без отдельной ручной команды.
  • Письма отправляет библиотека Nodemailer по SMTP (стандартному способу отправки почты). Куда — решает одна настройка: локально и в автопроверке на GitHub — Mailpit, на сервере — Resend. Ключ Resend только в .env сервера.
  • Mailpit добавляется в docker-compose.yml, открыт только для этого компьютера.
  • Новые строки .env: BETTER_AUTH_SECRET, BETTER_AUTH_URL, SMTP_URL, MAIL_FROM, OWNER_EMAIL. В .env.example — только имена. Строки вписываете вы.
  • Все прежние автотесты сначала входят под владельцем тестовой базы через Mailpit. Новые: вход, два пользователя, перенос данных владельцу; отдельно — проверка почты и текст письма.
  • В изменение не входят: роли, общий доступ к контактам, удаление пользователя.
