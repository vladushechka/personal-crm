# Design

## Context

- Контакты в `contacts`, список на главной — `listContacts(query)` в `src/lib/contacts.ts`, поиск кладёт запрос в адрес `?q=`
- Текст пользователя в запросах идёт через `safely()` из `src/db/safe-query.ts`
- Подход «сохраняется сразу» уже есть: поле частоты в карточке (`useOptimistic` + server action, `src/components/keep-in-touch-select.tsx`)
- В проекте есть Playwright, но нет быстрых автотестов. CLAUDE.md требует TDD: сначала тест, он красный, потом код
- `createDb` общий для приложения, сидов и e2e

## Goals / Non-Goals

**Goals:**
- Группы и состав — обычные таблицы со связью многие ко многим; удаление контакта или группы чистит связи само
- Быстрая обратная связь в карточке, как у поля частоты
- Правила названия проверяются Vitest, сценарии — e2e на настоящей базе

**Non-Goals:**
- Цвета и значки групп, вложенные группы, объединение групп
- Массовое включение нескольких контактов в группу из списка
- Выбор нескольких групп одновременно на главной
- Группы в форме добавления контакта: сначала контакт, потом его группы в карточке
- Настройка CI: урок 4.3

## Decisions

1. **Две таблицы.** `groups` (`id`, `name`, `created_at`) с уникальным индексом по `lower(name)`, и `contact_groups` (`contact_id`, `group_id`, первичный ключ из обоих, `on delete cascade` с двух сторон). Уникальность держит база, а не проверка в коде: так две вкладки не создадут дубликат. Альтернатива — массив в `contacts` — отклонена: переименование и счётчики становятся сложнее.
2. **Создание через `on conflict do nothing`, затем чтение** по `lower(name)`: и новая, и существующая группа обрабатываются одним путём.
3. **Групповая логика в `src/lib/groups.ts`**: контакты в `contacts.ts` остаются про контакты. Названия групп идут через `safely()`. Правила названия — `groupNameSchema` в `src/lib/group-schema.ts`, без зависимостей от базы, чтобы их проверял Vitest.
4. **Занятое название при переименовании** определяется по коду Postgres `23505`. `safely()` стирает детали ошибки, но оставляет код, поэтому переименование ловит конфликт заранее обычным запросом «есть ли другая группа с таким `lower(name)`», а гонку двух вкладок закрывает уникальный индекс: обе ветки дают «Такая группа уже есть».
5. **Фильтр через адрес `?group=<id>`**: ссылки работают в браузере и переживают обновление. `ContactSearch` сохраняет `group` в адресе. Кнопки-ссылки держат `q`, чтобы смена группы не сбрасывала поиск. Если группы с таким id нет, показываем все контакты.
6. **`listContacts(query, groupId)`** добавляет условие `exists` по `contact_groups`. Метки строки приходят отдельным запросом `contactId → названия групп` одним словарём: так основной запрос списка не меняется, а метки не дублируют строки.
7. **Кнопки групп в карточке** — `button` с `aria-pressed`, состояние через `useOptimistic`, как у поля частоты. Обычные чекбоксы не берём: нужен единый вид с кнопками на главной и удобное нажатие на телефоне.
8. **Страница `/groups`** — серверная, строка группы — клиентский компонент по образцу `note-item.tsx`: правка на месте, подтверждение удаления как в `delete-note-button.tsx`.
9. **Vitest** — только для кода без базы и браузера, команда `pnpm test`, секунды. Файлы рядом с кодом: `*.test.ts`. Сюда же тест `safely()`: любая ошибка, в том числе не из этой копии Drizzle, выходит без значений.
10. **Тестовые данные**: `assignFakeGroups(db)` в `scripts/seed-db.ts`, зовётся из `pnpm db:seed`, разовая команда `pnpm db:seed:groups`, e2e global setup её не зовёт: так сценарий «групп нет» проверяется на чистой базе.

## Risks / Trade-offs

- [Много групп на телефоне] → ряд кнопок переносится на новые строки; десятки групп займут много места, это приемлемо для личного списка
- [Метки отдельным запросом] → один лишний запрос на главную; на 1000 контактов это быстро, и индекс первичного ключа `contact_groups` подходит
- [e2e сценарий «групп нет» зависит от порядка] → файл тестов групп начинается с этого сценария, как и `keep-in-touch`
- [`lower()` в Postgres зависит от локали базы] → официальный образ `postgres:18` использует `en_US.utf8`, кириллица приводится верно; проверяется сценарием «такая группа уже есть»

## Migration Plan

1. `drizzle-kit generate` — новая миграция создаёт две таблицы и индекс; существующие таблицы не меняются
2. Выкатка обычная: шаг миграций → новая версия → smoke `/health`
3. После выкатки один раз на сервере: `pnpm db:seed:groups` из того же образа
4. Откат: предыдущая версия образа не знает о новых таблицах и работает как раньше
