# Design

## Context

- Контакт хранится в `contacts`, заметки в `notes` с `created_at`. Заметки теперь можно править и удалять, дата при правке не меняется (см. `src/lib/contacts.ts`)
- Главная (`src/app/page.tsx`) уже динамическая: читает базу на каждый запрос, есть поиск `?q=`
- Карточка (`src/app/contacts/[id]/page.tsx`) — серверная, правки идут через server actions в `src/app/actions.ts` с `refresh()` / `revalidatePath("/")`
- На сервере миграции применяет отдельный шаг выкатки до старта новой версии
- Тестовые данные: `insertFakeContacts` в `scripts/seed-db.ts`, её зовут `pnpm db:seed` (только пустая база) и e2e global setup (своя база `personal_crm_e2e`)

## Goals / Non-Goals

**Goals:**
- Посчитать «пора связаться» одним запросом к базе, без отдельного хранения даты последнего общения
- Не трогать существующие данные при миграции; предыдущая версия приложения работает с новой базой
- e2e-тесты фичи на настоящей базе, без подмены времени в приложении

**Non-Goals:**
- Уведомления и напоминания (почта, пуш) — в продуктовой идее прямо «не делать»
- Отметка «пообщались» без заметки, «отложить» человека, свои интервалы вроде «раз в 10 дней»
- Значки просрочки в общем списке контактов и в карточке — только блок на главной
- Часовой пояс пользователя: границы дней считаются по времени сервера

## Decisions

1. **Две колонки в `contacts`**: `keep_in_touch_frequency` (text, `week` / `month` / `quarter` / `year` или NULL, с CHECK) и `keep_in_touch_since` (timestamptz, NULL когда частота не задана). Отдельная таблица не нужна: связь один к одному. Text + CHECK вместо enum Postgres — новый вариант позже добавить проще.
2. **Последнее общение не хранится, а считается**: `max(notes.created_at)` по контакту. Так правка и удаление заметок учитываются сами, синхронизировать нечего. Альтернатива — колонка `last_contacted_at` с обновлением в каждом действии с заметками — отклонена: легко разъехаться.
3. **Срок в SQL**: `due_at = coalesce(последняя заметка, keep_in_touch_since) + интервал`, где интервал `7 days`, `1 month`, `3 months`, `1 year` — календарная арифметика Postgres. Пора — `due_at < now()`. Порядок — `due_at` по возрастанию (самая ранняя дата срока = больше всего дней просрочки), при равенстве — по имени. Индекс `notes(contact_id, created_at)` уже есть.
4. **Переключатель в карточке — обычный `<select>`** в стиле токенов: удобен на телефоне, доступен с клавиатуры, новых компонентов не нужно. Смена значения сразу вызывает server action; пока сохраняется — поле недоступно и крутится индикатор. Ошибка «Контакт не найден» показывается под полем.
5. **Server action `setKeepInTouchAction`** проверяет значение через zod, пишет частоту и `keep_in_touch_since = now()` (или обе NULL для «Не задано»), затем `revalidatePath("/")` и `refresh()`.
6. **Блок на главной** — серверный компонент в своём `Suspense` над поиском; показывается только без `?q=`. Все строки приходят с сервера, клиентская обёртка показывает первые 5 и раскрывает остальные по кнопке. Отдельная страница или `?all=1` — лишний переход ради одного действия.
7. **Тестовые данные**: функция `assignFakeFrequencies(db)` в `scripts/seed-db.ts` — примерно 10% контактов, случайная частота, `keep_in_touch_since` — случайная дата за последние полгода. Её зовёт `pnpm db:seed` после заполнения. e2e global setup её НЕ зовёт: в тестовой базе блок пуст, тесты сами создают нужные контакты. Для уже заполненной базы — разовый скрипт `pnpm db:seed:keep-in-touch`: выходит без изменений, если частота уже задана хоть у одного контакта.
8. **e2e с прошлыми датами**: тест создаёт контакт через интерфейс, а «старую» заметку или давнюю `keep_in_touch_since` выставляет прямым запросом в тестовую базу. Приложение не знает о тестах, моков нет.

## Risks / Trade-offs

- [Время сервера в UTC, а пользователь в Москве] → срок может наступить на 3 часа раньше или позже по местному времени; для «раз в неделю и реже» это незаметно
- [Тестовые данные на сервере меняются разовой командой] → команда ничего не делает, если частоты уже есть, поэтому реальный выбор пользователя не перезапишет; запускается вручную один раз
- [Много просроченных в блоке (на тестовых данных ~100)] → сначала видно 5, остальное по кнопке; все строки одним запросом — для 1000 контактов это быстро

## Migration Plan

1. `drizzle-kit generate` — миграция `0001`: две nullable-колонки и CHECK; существующие строки не меняются
2. Выкатка как обычно: шаг миграций → новая версия → smoke `/health`
3. После выкатки один раз на сервере: `pnpm db:seed:keep-in-touch` из того же образа (разовый контейнер, как миграции)
4. Откат: предыдущая версия образа работает с новыми колонками — откатываем образ вручную, колонки остаются
